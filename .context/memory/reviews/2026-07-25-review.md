## 3. Discovery — the store-layer map (corrects two ADR-11 premises)

**Premise correction 1 — "three SQLite DBs" is really two files.** ADR-11 lists
`odds.db`, `adaptive.db`, `audit_log.db`. `audit_log` is a *table* in
`adaptive.db` (AuditEventRepository uses the same `Base`), not a separate file.
The data-copy script treats it as one source.

**Premise correction 2 — "mostly a connection-string change" holds only for the
adaptive side.** Two completely different DB access patterns coexist:

- **betb2b store** (`src/sites/betb2b/store.py`, ~566 lines): raw `sqlite3`
  stdlib, hand-written SQL with SQLite-specific syntax (`ON CONFLICT(x) DO
  UPDATE`, `?` placeholders, `INTEGER PRIMARY KEY` autoincrement, `lastrowid`).
  NOT SQLAlchemy. The 13 store tests depend on `sqlite3.Row` string-key
  indexing + `sqlite_master` queries — a transparent connection swap would
  break them. Needed a real schema port (3-c), not a connection swap.
- **Selector Engine adaptive** (`src/selectors/adaptive/db/`): SQLAlchemy 2.0
  ORM, but 9 independent `create_engine(f"sqlite:///{db_path}")` call sites
  (8 repositories + `triage_metrics`'s embedded repo). This side WAS the
  connection-string swap (3-b).

## 4. Findings

### F1 — ADR-11's "connection-string swap" premise is half-right (Medium, addressed)
The adaptive side is SQLAlchemy → routing through one env-driven factory was
mechanical (3-b). The betb2b side is raw sqlite3 → needed the schema ported to
ORM models (3-c) before it can host on Postgres at all. Documented in the ADR
progress note so the next agent doesn't underestimate the persist-path rewrite.

### F2 — The betb2b persist path is still raw sqlite3 (High, backlogged)
`store.py`'s `persist_result`/`latest_odds`/`line_movement`/`cross_skin_odds`/
`counts` are raw SQL on a `sqlite3.Connection`. The ORM models (3-c) are the
canonical Postgres schema, but the live scraper still writes via the old path.
Swapping it is the largest remaining ADR-11 piece (~500 lines), high-risk (13
tests + CLI depend on the current conn API), and unverifiable on Postgres from
this sandbox. Backlogged with full context.

### F3 — Pre-existing FastAPI collection error blocks the adaptive/API test suite (Medium, pre-existing, backlogged)
`tests/integration/test_feature_flag_api.py` + `test_audit_api.py` fail at
**collection** with `fastapi.exceptions.FastAPIError: Invalid args for response
field! ... FailureService is a valid Pydantic field type`. **Verified pre-existing
via `git stash`** — reproduces on clean HEAD without this session's changes. Root
cause: installed fastapi 0.140.0 (project pins `>=0.110.0`) rejects
`FailureService` as a response-model annotation. Version drift, not introduced
here. Backlogged as an inefficiency.

### F4 — `triage_repository._create_indexes` queries `sqlite_master` (Low, backlogged)
SQLite-specific index-existence check. Wrapped in try/except so it won't crash
on Postgres (it'll skip silently), but the optimized triage indexes won't be
created there. Needs a dialect-aware `inspect()` check. Backlogged.

## 5. Fixes Applied (the four ADR-11 increments)

### `e03da90` — shared env-driven engine factory (`src/core/db.py`)
The single integration point: `DATABASE_URL` set → used verbatim (Railway
Postgres); unset → SQLite fallback (`ADAPTIVE_DB_PATH` then `data/adaptive.db`).
One SQLAlchemy code path, both backends, callers never branch on the URL scheme.
SQLite gets `check_same_thread=False`; `:memory:` uses `StaticPool` so test
sessions share one connection. `is_postgres()` lets migration/copy scripts skip
SQLite-only pragmas. 11 tests cover the precedence chain + `:memory:` sharing.
Deps: `psycopg[binary]` + `alembic` added to `pyproject.toml` + `requirements.txt`.

### `3629183` — adaptive repositories routed through the factory
9 `create_engine(f"sqlite:///...")` sites (8 repositories + `triage_metrics`)
→ `get_engine(db_path)`. Every `db_path` constructor arg preserved (callers/tests
unaffected). `Base.metadata.create_all()` calls untouched. No
`create_engine(f"sqlite...")` remains in `src/` outside `src/core/db.py`. All 10
refactored repository classes smoke-tested on `:memory:`, file path, and
`DATABASE_URL` override.

### `39e1c02` — portable betb2b ORM models + ADR-11 indexes (`src/sites/betb2b/models.py`)
13 ORM models mirroring `store.py`'s ADR-6 schema exactly, with portable types:
`SurrogatePK = BigInteger().with_variant(Integer, "sqlite")` (autoincrements on
BOTH backends — SQLite needs literal `INTEGER PRIMARY KEY` for rowid, `BIGINT`
would fail NOT NULL); `success`/`is_live`/`is_suspended` → `Boolean`;
timestamps → `DateTime(timezone=True)` (→ `timestamptz` on Postgres); `event_id`
stays a natural `Text` key. ADR-11 hot-path indexes added:
`odds_snapshots(event_id, captured_at)` + `events(start_time)`. Separate `Base`
from the adaptive layer (independent migration histories). 5 tests: tables
create, indexes present, SQLite-isms ported, DDL compiles for the PostgreSQL
dialect (BIGINT/BOOLEAN/TIMESTAMP WITH TIME ZONE, no AUTOINCREMENT leak),
persist-shaped insert round-trips.

### `c0802a2` — Alembic baseline + one-time data-copy script
`alembic/env.py` merges BOTH `Base` metadata → one migration stream for the
consolidated store. Baseline `c7ea08fedb55` (autogenerated) creates all 27
tables + every index; verified to apply cleanly. `scripts/migrate_sqlite_to_postgres.py`
copies the legacy `odds.db` (raw sqlite3 source, ORM write) + `adaptive.db`
(ORM read+write) into the target — proven to move rows (seeded 2, confirmed both
transferred). `--dry-run` for safe self-check.

## 7. Recommended Next Steps

The pattern across F1/F2 is the same lesson session 28 recorded one level up:
**a component's premise must be checked against how it's actually built, not
how the ADR text describes it.** ADR-11 said "SQLAlchemy 2.0 is already a dep,
so the engine swap is mostly a connection-string change" — true for the
adaptive half, false for the betb2b half (raw sqlite3). The next session should
finish F2 (the betb2b persist port) with a live Postgres to verify against,
then retire the Volume mount. Until F2 ships, the betb2b data still lands in
`odds.db` (SQLite) — the Postgres path exists at the model/migration level but
the scraper doesn't write through it yet.

## 8. Tool-flakiness note (flaws/log.md update)

This session hit the documented Bash-403 router outage (flaws/log.md sessions
12/25). Refined the root cause: the router rejects ANY command whose string
contains a secret (token-like pattern), and that rejection poisons the window
so even bare `echo` fails afterwards. Workaround proven: all multi-step work
goes through idempotent Python scripts written via the `Write` tool, executed
with **secret-free** command lines; the PAT is read from a file
(`/home/z/my-project/scripts/.pat`), never passed as a command arg. Logged to
`flaws/log.md` for the package.
