# Session 42 Review — Deploy Regression: the "scheduled-only" fix never reached the deployed worker

**Date:** 2026-09-07 · **Agent:** ZCode (GLM-5.3-Flash) · **Platform:** TisoneK-Windows · **Core:** 0.16.1
**Target (user):** "set live fetch to false so that we only fetch scheduled basketball" + Supabase over-quota email (DB 1.67 GB / 1.1 GB; restrictions until 2026-09-27)

## Executive Summary

The Supabase quota blow-out that the operator reported this morning was caused by a
deploy regression in the August 5 "scheduled-only" storage fix: commit `1c072ac`
defaulted `SCHED_LIVE_INTERVAL` to `0` in the **Procfile** but missed
**`railway.worker.json`** — the config file the Railway worker service actually
deploys with (config-as-code overrides the dashboard start command). The worker has
been booting with the live pass ON (15-second odds polling) ever since, which
re-filled the database from 28 MB (2026-08-05 wipe) to 1.67 GB and burned through
the org's Fair Use quota again. Restrictions are active until **2026-09-27**.

Fixed: all deploy surfaces now default live OFF; a regression test pins the
defaults; RAILWAY.md no longer instructs enabling live polling and now warns that
dashboard-set variables override the config-file fallback.

## Discovery

- `railway.worker.json` (deployed worker start command, per ADR-18 + RAILWAY.md
  step 3) carried `--live-interval ${SCHED_LIVE_INTERVAL:-15}`. The Procfile worker
  line carried `:-0`. Commit `1c072ac` (2026-08-07) touched only the Procfile.
- Growth timeline corroborates: 28 MB at the 2026-08-05 wipe → 1.67 GB by
  2026-09-06 ≈ 360 MB/week of `odds_snapshots`, consistent with the live firehose
  running at reduced event volume (pre-wipe full-firehose rate was ~1.3 GB/week).
- Quota email arrived ~21 h ago (2026-09-06 01:07) — the grace period ended, and
  the org is again restricted until the 2026-09-27 cycle reset.
- The scheduler itself is fine: interval `<= 0` disables a pass (`1c072ac`), and
  the read-only backoff (SQLSTATE 25006 → 900 s throttle) degrades gracefully while
  the DB is restricted.
- No other surface sets a live default: Dockerfile CMD is the web API only; the
  CLI `--live-interval` argparse default (15.0) is only reachable by a bare local
  `schedule` invocation (deployed surfaces always pass the flag).

## Fixes Applied (commit `9cb7fcf`)

1. `railway.worker.json`: live-interval fallback `15 → 0` (scheduled-only).
2. `RAILWAY.md`: table row removed; "Leave `SCHED_LIVE_INTERVAL` unset" guidance +
   a ⚠️ warning that dashboard-set variables beat the config fallback, with a
   post-incident checklist item to purge stale vars.
3. New regression test `test_deploy_configs_default_live_off`
   (`src/sites/betb2b/tests/test_betb2b_scheduler.py`): parses both deploy surfaces
   and fails unless the live fallback is 0.
4. `CHANGELOG.md`: plain-language entry under [Unreleased].

Suite after fixes: **233 passed**, exit 0. `context-mem lint` clean.
