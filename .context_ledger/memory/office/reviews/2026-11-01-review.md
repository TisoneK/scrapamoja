# Grader-lag diagnosis — 2026-11-01 (Tariq / S014)

**Operator report:** "I think the grader is a bit behind or not efficient."

Read-only investigation on Baos-Mac-mini against the shared **local Postgres**
(`localhost:5432/scorewise`, the ADR-7 cutover target). No scrape or live fetch
was run; all evidence is from the store, the launchd jobs, and the scrape log.

## Short answer

The **scraper is not behind** — it is current to the minute. The **grader is
mildly behind**, by a cadence gap, and that part lives in scorewise-engine, not
here. There is a **real efficiency problem on the scraper side** feeding the
results pass, which is fixable here.

## What the evidence shows

**Scraper / results pass — healthy.**
- `results` ran **58×** in the last 24h (≈ every 30 min; last at **06:52 UTC**,
  minutes before this check). Full `list_prematch` scrape ran 4× (every 6h, ~352s,
  196 events). Jobs are on cadence — `com.scrapamoja.scrape` and
  `com.scrapamoja.results` are both loaded and firing.
- **335** basketball results filled in the last 24h, 1260 in the last 7d. Last
  result written 06:52 UTC.

**Results backlog — source-side, not a scraper fault.**
- basketball events (real; non-alternative, non-superseded): 2056 resolved
  (`result_status=3`), 448 given up after 7d (`-1`), 6 void (`-2`), 658 with no
  status yet. Of those 658, **~276 are finished games past their 2.5h window still
  awaiting a result** (55 <1 day, 74 1–3 days, 147 3–7 days). The rest are upcoming.
- These are overwhelmingly games the **source has not published a result for**
  (the scrape log is full of `204 No Content` for them) — not games the scraper
  failed to fetch. They resolve when the source fills them, or hit the 7-day
  give-up.

**Grader — a bit behind (engine's lane).**
- predictions: 15,111 total, 13,049 graded, 2,062 ungraded. The ungraded are
  almost all events with no result yet — **only 3 resolved events (30 rows) are
  actually waiting on the grader**, 2 of them <6h old.
- Freshness gap: last result filled **06:52 UTC**, but last `prediction_grade_detail`
  / last `paper_bets.settled_at` = **04:50 UTC**. So grading last ran ~2h ago while
  results kept landing. paper_bets: 29,697 settled / 6,692 open; real_bets: 8 settled.
- Read as: the grader's run cadence trails the results cadence. It is not stalled
  (the backlog it can act on is tiny and fresh); it just runs less often than
  results arrive, which is what "a bit behind" looks like.

## The scraper-side inefficiency (fixable here)

`store.events_needing_results(min_age_seconds=9000, limit=200)` (store.py:1744)
selects **every** `result_status IS NULL` event older than 2.5h, oldest first,
with **no per-game backoff**. A finished game whose source returned `204` is
re-asked on **every** 30-min run until the 7-day `give_up_results` flips it to
`-1`. With ~276 pending games and 58 results runs/day, that is hundreds of
mostly-`204` requests per run to fill a handful (`340 pending → 1 finished` in
the log) — against the "be gentle with the reverse-engineered endpoints"
preference, for near-zero yield on the stale tail.

Contrast: H2H and match-stats probes already remember a `not_offered` answer and
wait 24h (`coverage` table). Results have only the all-or-nothing 7-day give-up,
nothing in between.

## Recommendations

1. **Scraper (safe, here — needs operator OK because it changes result-pickup
   cadence).** Add a tiered re-ask backoff to `events_needing_results`, keyed off
   age since start, so **fresh games keep full cadence** (no added latency where
   the grader cares) and only the stale tail backs off:
   - <24h past start → every run (unchanged);
   - 1–3 days → ~hourly;
   - 3–7 days → every few hours.
   Still records gaps, still gives up at 7 days — no data omitted, just far fewer
   redundant `204`s. Mirrors the existing `coverage` 24h-wait pattern.
2. **Grader (engine — flagged, not mine to change).** The ~2h grade gap is the
   `com.scorewise.grade` job cadence trailing the 30-min results cadence. If the
   operator wants grading tighter, raise that job's frequency or trigger a grade
   pass after each results run. Scraper-side data is ready for it.
