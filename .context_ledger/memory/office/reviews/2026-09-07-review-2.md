# Session 43 Review — Local fallback store (Supabase outage/restriction → SQLite + outbox replay)

**Date:** 2026-09-07 · **Agent:** ZCode (GLM-5.3-Flash) · **Target:** operator request — "db fallback where if supabase fails or gets restricted we switch to local storage db"

## Executive Summary

Shipped the local fallback store: when a write to the primary store (Supabase
via `DATABASE_URL`) fails with a restriction or outage error, the scraper now
**switches to a local SQLite store** instead of dropping writes (the previous
behavior — ADR-21 §1b's scheduler backoff — lost every write for the whole
restriction window, currently until 2026-09-27). Writes made while degraded
are queued in an outbox and **replayed automatically** through the store's own
dedup paths when a throttled write-probe proves Supabase is writable again.
One commit (`ce24540`), 14 new tests, full suite 247 passed, RAILWAY.md +
CHANGELOG updated.

## Discovery (Phase 1 highlights)

- Current state (from memory + operator): DB 1.67 GB / 1.1 GB, Fair-Use
  restrictions active until 2026-09-27 — **the feature is live-relevant right
  now**; every scheduled pass (3h) currently writes into the void.
- Write seams: `store.init_db` → conn; `store.persist_result(result, path,
  conn)` dispatches to `store_orm` (Postgres/Supabase) or the sqlite3 branch;
  `store.record_result` for the results pass; scheduler `_loop` backs off on
  read-only errors (drops the pass's data).
- ADR-13 (Supabase shared store), ADR-21 §1b (read-only backoff, 25006
  detection), ADR-23 (egress constraints) all constrain the design.

## Design (see ADR-24 for the full decision)

1. **Failover:** `store.persist_result` / `store.record_result` wrap the ORM
   write; a fallback-eligible failure (25006 read-only, connection-class 08xx,
   resource 53xxx, shutdown 57P0x) activates fallback mode and applies the
   write to a local SQLite mirror (same schema). Non-eligible errors
   (auth 28P01, integrity/programming errors, pool timeouts) raise loudly.
2. **Outbox:** every fallback-mode write is appended (JSON payload) to
   `fallback_outbox` in the mirror. Replay dispatches per kind
   (`persist` → full scrape result; `result` → record_result op) through the
   store's normal upsert + change-only-dedup paths → idempotent, chronology
   preserved via payload `captured_at`.
3. **Probe + drain:** after each fallback write (throttled, default 300 s) a
   throwaway `INSERT…ROLLBACK` tests the primary — reads stay allowed while
   restricted, so only a write proves recovery. Success → flip back → drain
   (bounded 500 payloads / 60 s per pass; leftovers drain on later primary
   writes). Drain failure mid-replay re-activates fallback, rows stay queued.
4. **Seams:** `init_db` short-circuits to the mirror while fallback is active
   (no doomed primary write attempts per pass — the probe is the only primary
   traffic) and on connect failures. `scraper_jobs` (control queue) is
   deliberately NOT outboxed — coordination must stay cross-service coherent;
   remote job submission fails loudly during an outage.
5. **Config:** `BETB2B_FALLBACK=0` disables; `BETB2B_FALLBACK_DB_PATH`
   (mirror path; default = local-mode store path), `…PROBE_SECONDS` (300),
   `…OUTBOX_MAX` (5000, oldest dropped), `…DRAIN_MAX` (500).

  Volume option via `BETB2B_FALLBACK_DB_PATH`).
