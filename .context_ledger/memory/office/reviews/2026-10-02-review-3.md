# Session 50, open-items round — guarding the direct calls, resting a struggling site, pacing (2026-10-02)

Ada (S448). After the operator worked the repo (Session 51 added a security guard and persistent browser profiles), they asked me to finish the open backlog items except the proxy pool. This report covers that round; the decisions are in ADR-30.

## What changed

- **The scraper's direct HTTP calls now obey the guard** (B-11). The statistics, head-to-head, final-score and landing-page requests used to bypass it, so a Gcore challenge page there was parsed as data once per match. They now check the cooldown first, classify the response, and a block stops the whole batch with one warning. Result fetches report FAILED, so the stat-id breaker trips.
- **No-browser mode skips the browser rungs** (B-13). In direct mode there is no page to wait on or stronger browser to open, so a first challenge goes straight to failover or cooldown instead of being silently retried.
- **`probe` tells the truth** (B-14): "harvested" means cookies came back, and the guard's state is included.
- **One shared rest for a site that stops answering, plus an optional hourly budget** (B-2). Timeouts and dropped connections count in the same ledger as blocks: six in a row (configurable) rest the skin for five minutes, doubling per streak, for every component. `BETB2B_HOURLY_BUDGET` (off by default) caps requests per hour.
- **Per-second pacing** (new, from the live run below): `BETB2B_MAX_RPS`, default 3.
- **A guarded `reset` command** (B-6): dry run by default, `--force` to delete, `--also-local` to clear the replay queue too.
- **Docs** (B-7): ids are mostly, not always, identical across skins; the Railway guide is marked legacy.

## The live run, and what it showed

One gentle run on betwinner (before pacing existed) discovered 492 events, skipped 328 already stored, fetched 164 and got 67 events. Then every statistics, head-to-head and stat-id call timed out; the new rest fired as designed. That exposed two design flaws in my rest logic, both fixed: failures already in flight when a rest began kept doubling it (600 s, 1200 s, 2400 s), and a slow optional endpoint rested the whole skin including the odds feed. Statistics, H2H and result calls now rest only their own group.

More important: afterwards betwinner, melbet and 22bet all refused even the TCP connection from this machine. The run had sent about twenty requests a second (164 match requests in roughly eight seconds): four workers on a fast site, with the client's spacing switched off because "the semaphore is the throttle". That, not a dead site, is the most likely cause of every "unreachable" episode today. A per-skin pacer now bounds requests per second across the feed client and the direct calls.

## What is not verified

The live check after pacing did not happen: the hosts were still refusing connections when the round ended. B-12 (a real warm-up or hand-off against a challenge) needs an allowed-country connection and the operator. The proxy pool was excluded by the operator.

## What to do next

When the hosts answer again, run one scrape with pacing and confirm it completes without the drops; if they recur, lower `BETB2B_MAX_RPS`. Rotate the proxy password (operator). Decide whether linebet is worth supporting.
