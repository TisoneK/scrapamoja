# Session 50 — betb2b store, skip-processed, and the data audit (2026-10-02)

Ada (S448, claude-sonnet-5-5), Baos-Mac-mini. The operator asked for local SQLite as the main store with an optional shared remote database, no re-scraping of matches already stored (except to update scores), and then for the database to be audited and fixed. This report is for the project owner; the decisions are in ADR-26 and ADR-27.

## What happened

`scrape` now saves to the local SQLite file by default; `DATABASE_URL` (the operator's Neon Postgres, `BETB2B_STORE_MODE=mirror`) turns the same run into a shared-store run. `--skip-processed` never re-fetches a stored match, a started match, or an id known to be a sub-game, and a results update records final scores after each run. Settings live in the untracked `src/sites/betb2b/.env`. A shared JSON file as the remote store was rejected (no atomic claims, concurrent writers overwrite each other); Vercel was ruled out for running the scraper (no long-running workers) — only Postgres was ever needed from it.

Hardening followed: failed match fetches (timeouts, blocks) are retried with backoff and can be recovered on other skins; a blocked discovery is a failed run; parallelism dropped from 8 to 4; the stat-id steps stop after six consecutive failures instead of waiting out every timeout.

## What the audit found

A read-only audit of the Neon store (334 events) found nothing wrong with names, prices, orphans or market naming, and these problems:

- **Relisted matches (7 groups).** I first called them duplicates; the operator pointed out they might be period splits. Checking the live feed showed they are not: the bookmaker re-lists a match under a new, higher id, the old id then returns nothing, and periods are sub-games inside one event. Fixed non-destructively with `events.superseded_by`. My first rule linked a real match to its one-market sub-game stub because the stub had the higher id; caught during the backfill, fixed (a replacement must be as complete), and the bad link reverted.
- **Sub-games and junk stored as matches.** A sub-game id (parent+N, one special market, no venue) and nine "Home (Points) / Away (Points)" listings were stored as events. New scrapes drop them; the operator-approved cleanup deleted the 10 existing rows.
- **Failed discovery recorded as success.** Two blocked runs were stored as "0 events, success". New runs record the failure; the two rows were corrected.
- **No `stat_game_id` on any event.** Capture was added and a bounded backfill runs each scrape, but it is **unverified live** (0/37 and 0/150 when the sites were dropping connections).

## What the offline end-to-end test caught

A test replaying recorded feed responses through the real scraper, store, linking, skip pass and engine export (on raw SQLite and the Postgres-path store) found three bugs in my own earlier work: a normal "everything already stored" run was flagged as blocked; the sub-game lookup crashed on the Postgres-path store; and in `mirror` mode the skip check read only the local copy, so a second machine would have re-scraped everything. All fixed with tests.

The operator flagged it; the slips are in the inefficiencies log and corrected here.
