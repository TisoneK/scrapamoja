# Kenyan machine: how linebet's challenge appears, the two bugs it exposed, and where the runs stand

Session 53 — Achieng (S451), ZCode / deepseek/deepseek-flash, Lameck-Windows,
2026-10-03. Task: the Kenya-machine brief (`docs/proposals/KENYA_MACHINE_BRIEF.md`)
plus the operator's direction: find out how linebet's browser security appears
and fix it so linebet scrapes like the other skins.

Everything below was measured today from a Nairobi (Safaricom) egress, no proxy.

## What the challenge is, and how it behaves

- **Two layers.** A country block on the website (HTTP 203 → `/en/block` for
  disallowed countries) and, on top, a Gcore WAAP "browser validation" page —
  served with **HTTP 200** and an HTML body (title `Gcore`), running the
  `/sbbi/` SBBI flow and setting a clearance cookie (`sbtsck`) plus site
  protection cookies (`SPSI`, `SPSE`, `PRLST`, `spcsrf`, `sp_lit`).
- **A real browser passes it automatically.** Headless Chromium cleared it in
  ~3 s (the grid rendered 2.9 s after navigation); no person was needed once the
  profile existed. The operator's observation is confirmed by a controlled
  test: a **fresh context is challenged on its first load; the same context
  never is again**; a new context (even in the same browser) must re-pass.
- **The clearance is cookie-bound and not permanent.** The profile warmed at
  18:06 was re-challenged at 19:00 — the browser cleared it again itself in
  ~3 s. Nothing about the country: same address throughout.
- **Plain HTTP needs the full cookie jar.** With the browser's complete cookie
  set, `httpx` gets real JSON from both the feed (`GetGameZip`) and
  `statisticfeed` (`h2h`). With any subset — `sbtsck` alone, the whole
  `sp*`/`SPSI`/`SPSE`/`PRLST` family, everything except `sbtsck` — every
  request gets the challenge page. The WAF session cookies are part of the
  credential.
- **The endpoints differ in strictness.** With a freshly-earned clearance both
  endpoints answer; by ~4 minutes the `statisticfeed` path served the
  "Loading site please wait" interstitial while the feed path still answered
  JSON (probe: JSON at t≈6 s and t≈122 s, interstitial at t≈244 s). The H2H
  probes are also the ones that ran last in a scrape, minutes after bootstrap —
  which is exactly when they were challenged.

## The two real bugs this exposed (both fixed, both pushed, both tested)

1. **The harvested Cookie header dropped every session cookie** (`ec05ca0`).
   Playwright reports a session cookie's expiry as `-1`, and
   `SessionPackage.to_cookie_header()` treated any value below "now" as
   expired — so `SPSI`/`SPSE`/`PRLST` (and every other session cookie) never
   reached the wire. Live A/B on the same URL, same moment: full context
   cookies → JSON; the header exactly as the scraper built it → challenge
   page. Only positive deadlines in the past are skipped now. Regression test
   pins `expires=-1`.

2. **A burst of challenges walked the guard's ladder once per response**
   (`fb32cd1`, `6fa14bb`). Concurrent responses to one incident each called
   `guard.on_block`, so five simultaneous challenges burned four rungs in one
   second and rested the whole site for six hours — the 21,600 s cooldown that
   aborted the first dry run while its main data path was healthy.
   `guard_response` now reports whether a response was a block; the H2H,
   statistics and stat-id batches stop after the first one (the requests
   already in flight skip the guard) and leave the rest for another run;
   single fetches treat a challenge page as a failed fetch instead of parsing
   HTML as JSON.

3. **The bootstrap harvested cookies too early** (session.py, pushed).
   Probes that waited for the betting grid (`.dashboard-champ`) got working
   cookies; the scraper's own harvest — taken as soon as the challenge page
   disappeared — got challenged again. The bootstrap now waits (bounded,
   15 s, best-effort) for the grid before harvesting. Evidence-based, and the
   most likely remaining piece of the linebet story, but **not yet verified
   end-to-end** (see below).

Also fixed at the baseline, all Windows-only pre-existing failures: the store
fallback did not classify psycopg's "connection timeout expired" as
connectivity (`9e439bd`); a snapshot-cap test compared a Windows path to a file
name (`479d43b`); the Pacer collapsed concurrent starts on Windows' ~15.6 ms
timer — its own test could not see it because it measured with the same coarse
clock (`624c94e`).

## Where the runs stand

- **betwinner** — completed and persisted from this machine (store shows 377
  events for the skin). The CLI then hung ~12 minutes and exited 1; the data
  was already written.
- **melbet** — I killed it mid-run by mistake (took its process for a hung
  one; the loop had already moved on). Its earlier stored data is intact; it
  needs a re-run.
- **22bet** — completed (an unreachable streak rested it 4 minutes mid-run;
  the fallback logic recovered 198 ids) and persisted.
- **linebet** — bootstraps pass reliably (with and without a person, ~3 s to
  clear), and the feed path ran healthy for 2+ minutes in the 18:21 dry run.
  After the cookie fix the scraper's own harvest still hit the challenge —
  which is what the grid-wait change targets — but by then the address had
  taken a long evening of challenge hits, the site was challenging
  consistently, and the guard rested it for ~4 hours (19:21). **Live
  end-to-end verification with all three fixes in place is the open item**;
  run it in a fresh window, from a rested address.
